# 단계: 검증

기능: $FEATURE

## 출력 (이 파일 하나만 쓴다)
$WORK/VERIFY.md

## 산출물 외에 수정해도 되는 것
- DESIGN.md 의 `TEST_FILES` 블록에 있는 파일만 — 셸이 단계 전후 지문으로 대조한다.
  `ALLOWED_FILES` 안이라도 `TEST_FILES` 밖의 파일(소스)을 바꾸면 그 자리에서 죽는다.
  **구현이 틀렸다고 판단해도 소스를 고치지 않는다** — 그건 VERIFY.md 에 적어 올릴 일이다.

## 입력 (읽기만, 절대 수정 금지)
- `$WORK/DESIGN.md` — "검증 기준" 섹션이 테스트의 근거다
- `$WORK/IMPL.md` — 실제 구현 내용. "다음 단계가 알아야 할 것"에 낡은 테스트 인계가 있을 수 있다

## 할 일

1. DESIGN.md 의 검증 기준을 실행 가능한 테스트로 옮긴다.
2. 테스트를 작성/수정한다. **TEST_FILES 에 있는 경로만** — 셸이 지문으로 대조한다.
3. `$WORK/VERIFY.md` 에 기록한다.

## 이 저장소의 테스트

```bash
# 백엔드 — hymn-db-1 컨테이너가 떠 있어야 한다
cd backend && python -m pytest -q
python -m ruff check src tests alembic

# 프론트 (jsdom + vitest)
cd frontend && pnpm test
pnpm typecheck && pnpm lint && pnpm build
```

- 백엔드 테스트는 `backend/tests/` 에 있고 `conftest.py` 가 `APP_ENV=test`·
  `EMAIL_SENDER=console`·`PASSWORD_RESET_ENABLED=true` 를 **앱 import 전에** 세운다.
  안 세우면 전 스위트가 import 에서 죽는다 — 새 conftest 를 만들지 말고 기존 것을 쓴다.
- **스키마를 바꿨다면 마이그레이션 자체를 테스트한다.** 모델이 맞는 것과 마이그레이션이
  도는 것은 다른 문제다. up → down → up 왕복, 그리고 **기존 데이터가 있는 상태에서의 up**
  (운영에는 150행이 있다)을 확인한다.

## 테스트를 쓸 때 지킬 것

- **구조 불변식은 값이 통째로 바뀌어도 통과한다.** "필드가 3개다", "리스트가 비어있지 않다"
  같은 단언은 회귀를 못 잡는다. **값을 고정**하거나 관계를 단언한다.
- **의심한 곳만 검증하면 의심한 것만 잡힌다.** 검증 기준에 없더라도, 구현이 건드린
  경계(NULL, 빈 목록, 중복, 순서)를 스스로 찾아 케이스를 추가한다.
- **`GET /scores` 의 정렬·응답 필드를 고정하는 테스트가 이미 있는지 확인하고,
  없으면 만든다.** Flutter 앱과의 공유 계약인데 지금 이걸 지키는 테스트가 없으면
  다음 사람이 조용히 깬다.

## VERIFY.md 필수 섹션

- STATUS 라인 (첫 줄)
- 작성한 테스트 파일과 케이스 목록
- 검증 기준 ↔ 테스트 케이스 대응표 (**빠진 기준이 있으면 명시**)
- **각 테스트가 무엇을 깨면 실패하는지** 한 줄씩 — 이게 없으면 통과해도 의미를 모른다
- 테스트로 덮지 못한 부분

## 중요

- 테스트 통과 여부는 **이 세션이 판정하지 않는다.** 파이프라인이 별도로 실행한다.
  "통과할 것으로 보인다" 같은 문장을 쓰지 마라.
- **구현이 명백히 틀렸다고 판단되면 테스트를 느슨하게 만들지 말고 `STATUS: BLOCKED`.**
  이 단계의 유일한 실패 모드는 통과하는 테스트를 만들려고 기준을 낮추는 것이다.
- **제품 코드를 고치지 않는다.** 구현이 틀렸으면 BLOCKED 로 올린다.
