## 입력 (읽기만, 절대 수정 금지)
- `$WORK/BRIEF.md` — **여기서 시작한다.** 사람·런처가 미리 추린 과제 요약과 관련
  파일 목록이다. 저장소를 처음부터 훑지 말고 이 목록의 파일부터 읽어라.
  **이것은 시작점이지 경계가 아니다** — 목록 밖 파일이 필요하면 그냥 읽어라.
  목록이 틀렸거나 부족하면 그 사실을 DESIGN.md 에 한 줄로 남겨라(다음 실험의 근거다).
  파일이 없으면 없는 대로 진행한다 — BLOCKED 사유가 아니다.
- `$ROOT/.claude/handoff.md` — **이 저장소의 결정 이력·지뢰 정본.**
  **이 파일이 없으면 즉시 `STATUS: BLOCKED`.** 근거 없이 설계하지 않는다.
  최소한 읽을 것: 상단 "지금 상태" 블록 · 1-A절(상시 지뢰) · 9절(미뤄둔 것·별건 버그)
- `$ROOT/.claude/research-*.md` — 있으면 읽는다. 최근 리서치의 측정값이 들어 있다
- `$ROOT` 의 관련 코드

## 이 저장소의 구조

```
backend/src/app/     FastAPI. models.py · schemas/ · routes/ · services/ · deps.py
backend/alembic/     마이그레이션. 스키마를 바꾸면 여기도 반드시 함께 바뀐다
frontend/src/        React + Vite. features/ · pages/ · api/ · lib/
hymn_app/            Flutter. **리포 루트에 중첩된 별도 git 저장소** (모노리포 아님)
```

## ★ 이 저장소에서 밟으면 되돌릴 수 없는 것 — 설계 전에 반드시 확인

1. **`GET /scores` 는 Flutter 앱이 호출하는 유일한 엔드포인트다**
   (`hymn_app/lib/data/scores_api.dart`). 정렬(`routes/score.py` 의 `created_at.asc()`)도
   응답 스키마도 **앱과의 공유 계약**이다. 앱에는 자체 업데이트 수단이 아직 없어서,
   깨면 교회 태블릿이 그날로 멈추고 복구가 안 된다.
   **이 엔드포인트의 응답 형태를 바꾸는 설계라면 하위호환 경로를 반드시 함께 설계한다.**
2. **`churches` 를 참조하는 `users`·`scores` 가 둘 다 `ondelete="CASCADE"` 다.**
   교회를 지우면 그 안의 계정이 함께 사라진다.
3. **마이그레이션은 새 코드보다 먼저 돈다** (`deploy.yml`). 코드가 참조하는 컬럼은
   그 배포의 마이그레이션에 반드시 포함돼야 한다. 반대로 **컬럼 삭제는 코드가 먼저 나간 뒤**다.
4. **운영에 실제 데이터가 있다** — 교회 1개, 계정 1명, **악보 160행 / 85곡**(2026-09-05 실측).
   스키마를 바꾸면 이 160행을 어떻게 옮길지가 설계의 일부다. 마이그레이션은
   **각 단계마다 rowcount 를 단언**하고, 순서(이동 → 잔여 0 확인 → 삭제)를 안전장치로 쓴다.

## 할 일

1. 관련 코드와 handoff 를 읽고 현재 구조를 파악한다.
2. 설계를 `$WORK/DESIGN.md` 에 쓴다.

## DESIGN.md 필수 섹션

- STATUS 라인 (첫 줄)
- **근거 있는 현황 서술** — 아래 "근거 등급" 규칙을 따른다
- 변경 대상 파일 목록 (경로 명시, 신규/수정 표시)
- 공개 인터페이스 (함수 시그니처 / API 스펙 / 스키마 / 마이그레이션 revision)
- 데이터 흐름 (입력 → 처리 → 출력)
- **마이그레이션 계획** (스키마를 건드리는 경우) — up/down, 운영 150행 처리, rowcount 단언 지점
- **하위호환** — `GET /scores` 등 앱·웹이 이미 쓰는 계약을 건드리면 여기에 적는다. 안 건드리면 "해당 없음"
- 검증 기준: "됐다"를 무엇으로 확인하는지 **테스트 케이스 수준으로**
- 하지 않는 것 (범위 밖 명시)
- `ALLOWED_FILES:` 블록과 `TEST_FILES:` 블록 (아래 형식 엄수 — 셸이 파싱한다)

## 근거 등급 — 주장마다 붙인다

다음 단계(판단 검증)가 이걸 감사한다. 등급 없이 단정하면 전부 `추정`으로 취급된다.

- **실측** — 도구를 실제로 돌린 출력이 근거. 명령과 출력 요약을 함께 적는다
- **코드확인** — `파일:줄` 로 짚을 수 있다. **경로와 줄번호를 반드시 본문에 적는다**
  — 다음 단계(판단 검증)가 이 좌표로 직행해서 확인한다. 좌표 없는 코드확인 주장은
  그 단계에서 재탐색 비용을 만들고, 등급도 `추정` 으로 강등된다
- **추정** — 위 둘이 아닌 전부

확인 비용이 도구 호출 1~2회면 **확인하고 쓴다.** 특히:
- **"X가 없다"는 부재 주장은 전수 확인 후에만** — 백엔드·프론트·Flutter 셋을 다 본다
- 운영 현황은 실측할 수 있다: `curl -s https://www.score-hymn.com/api/scores`
  (`GET /scores` 는 아직 무인증 공개다. 읽기 전용이므로 안전)
- **handoff 의 "반증된 것" 목록에 있는 주장을 되살리지 않는다**

## ALLOWED_FILES 블록 (형식 엄수 — 셸이 파싱한다)

"변경 대상 파일 목록" 과 **별도로** 아래 블록을 정확히 이 모양으로 넣는다.
목록은 사람이 읽고 이 블록은 셸이 읽는다. 둘의 내용은 일치해야 한다.

ALLOWED_FILES:
- backend/src/app/models.py
- backend/tests/test_foo.py

규칙:
- 저장소 루트 기준 상대 경로. `./` 접두사 금지.
- 한 줄에 하나, `- ` 로 시작. 블록은 빈 줄로 끝난다. 주석·설명을 섞지 않는다.
- 구현이 새로 만들 파일, **검증 단계가 만들 테스트 파일까지 미리 다 넣는다.**
- **alembic 마이그레이션 파일을 빠뜨리지 말 것.** 파일명에 revision 해시가 들어가는데
  그건 구현 시점에 정해지므로, `backend/alembic/versions/` 아래 경로를 미리 확정해 적는다
  (예: `backend/alembic/versions/<revision>_split_song_usage.py` 처럼 쓰지 말고,
  revision 을 설계에서 직접 정해 **완전한 파일명**으로 적는다)
- 여기 없는 파일이 변경되면 파이프라인이 그 자리에서 죽는다. 재시도가 아니라 종료다.
- 목록이 길어지는 게 부담이면 설계 범위가 넓은 것이다. 목록을 줄이지 말고 범위를 줄여라.
- **여기 넣는 기존 파일은 전부 Read 로 열어봐야 한다.** 셸이 이 세션의 도구 호출 기록에서
  확인하고, 안 읽은 파일이 하나라도 있으면 판단 검증을 띄우지 않고 죽인다. 열어보지 않은
  파일을 고치겠다는 설계는 그 자체가 누락이다. Grep 으로 스친 것은 읽은 것이 아니다.

## TEST_FILES 블록 (형식 엄수 — 셸이 파싱한다)

`ALLOWED_FILES` 중 **테스트 파일만** 다시 적는다. 같은 형식, 같은 규칙이다.

TEST_FILES:
- backend/tests/test_foo.py

셸은 이 블록으로 "누가 어느 파일을 고쳐도 되는가"를 가른다 — 구현 단계는 여기 있는 파일을
바꾸면 죽고, 검증 단계는 여기 **없는** 파일을 바꾸면 죽는다. 그래서:
- 검증이 고쳐야 할 기존 테스트(낡은 테스트)와 새로 만들 테스트를 전부 넣는다.
- 소스 파일을 여기 넣지 않는다 — 검증이 소스를 땜질할 수 있게 되고, 그건 이 블록이 막으려는 것이다.
- **블록은 반드시 있어야 한다.** 테스트 파일이 없는 설계라면 헤더만 쓰고 빈 줄로 닫는다.
  빠뜨리면 판단 검증을 띄우기 전에 죽는다(비용 $0 이지만 한 바퀴를 버린다).
- 여기 있는 파일은 `ALLOWED_FILES` 에도 있어야 한다. 아니면 설계 직후 죽는다.

## 검증 가능성 — 설계 단계에서 정해진다

검증 기준을 쓸 때 두 가지로 나눠라:
- **[테스트 가능]** — 셸이 `$TEST_CMD` 로 돌려서 판정할 수 있는 것
- **[사람 확인 필요]** — 못 돌리는 것 (실제 S3·SES, 타이밍, UI 육안 확인, 운영 DB)

**검증 가능한 쪽으로 구조를 밀어라.** 라우트 핸들러 안에 로직을 묻지 말고 순수 함수로
빼면 그만큼 [테스트 가능] 으로 넘어간다. 부작용(I/O·네트워크·시계)과 판정 로직의 분리가 그 축이다.

## 게이트에 걸리는 것 — 설계에 넣지 말고 STATUS: BLOCKED 로 올려라

- 의존성 추가/제거 (`backend/pyproject.toml`·`frontend/package.json` 등 — 사람 승인 사항)
- 테스트 러너·린터 설정 변경 (`pytest.ini`·`vitest.config.ts`·`ruff` 설정)
- 셸이 보호하는 파일(`PROTECTED_FILES`)을 바꿔야만 되는 설계
- `.claude/handoff.md`·`CLAUDE.md` 수정

## 금지

- 코드를 쓰지 않는다. 시그니처와 스펙까지만.
- 설계에 필요한 정보가 없으면 추측하지 말고 `STATUS: BLOCKED`.
- **`.claude/handoff.md` 를 수정하지 않는다.** 결정 이력의 정본이고 사람이 관리한다.
