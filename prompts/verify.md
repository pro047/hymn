# 단계: 검증 (테스트 선작성)

기능: $FEATURE

이 단계는 **구현 전에** 돈다. 설계의 검증 기준을 실행 가능한 테스트로 먼저 고정한다.
구현은 아직 없다 — 네 테스트는 지금 코드에서 **실패해야 정상**이다.

## 출력 (이 파일 하나만 쓴다)
$WORK/VERIFY.md

## 산출물 외에 수정해도 되는 것
- DESIGN.md 의 `TEST_FILES` 블록에 있는 파일만 — 셸이 단계 전후 지문으로 대조한다.
  `ALLOWED_FILES` 안이라도 `TEST_FILES` 밖의 파일(소스)을 바꾸면 그 자리에서 죽는다

## 입력 (읽기만, 절대 수정 금지)
- `$WORK/DESIGN.md` — "검증 기준" 섹션이 테스트의 근거다
- `$WORK/JUDGE.md` — 설계 주장 감사 결과. `반박` 판정이 난 주장을 전제로 테스트를 쓰지 마라

## 이 저장소의 테스트 환경

허용된 명령은 **정확히 이 형태**다 (다른 형태는 헤드리스에서 거부된다):

```bash
# 백엔드 — hymn-db-1 컨테이너가 떠 있어야 한다
cd backend && .venv/bin/python -m pytest -q
cd backend && .venv/bin/ruff check src tests alembic

# 프론트 (jsdom + vitest)
cd frontend && pnpm test
cd frontend && pnpm lint
cd frontend && pnpm format:check
cd frontend && pnpm typecheck
```

- **★ 네 테스트 파일은 ruff(import 정렬 포함)·eslint·prettier 를 통과해야 한다.** 셸의 검증 목록에
  린트·포맷 검사가 들어 있고, 구현은 테스트 파일을 한 글자도 못 고친다 — 형식이 어긋난 테스트 하나면
  green 에 영영 못 가고 재시도만 소진한다. 제출 전에 위 검사 명령으로 **네 파일**이 깨끗한지 확인하라.
  형식 실패는 "잘못된 실패"다 (아래 할 일 4).

- 백엔드 테스트는 `backend/tests/test_*.py` 에 있고 `conftest.py` 가 `APP_ENV=test`·
  `EMAIL_SENDER=console`·`PASSWORD_RESET_ENABLED=true` 를 **앱 import 전에** 세운다.
  안 세우면 전 스위트가 import 에서 죽는다 — 새 conftest 를 만들지 말고 기존 것을 쓴다.
  같은 conftest 가 S3 존재 확인(`get_object_probe`)을 "있음" 으로 덮는다 — 실 S3 를 부르지 않는다.
- 프론트 테스트는 소스 옆 `*.test.{ts,tsx,js,jsx}` 다 (vitest + jsdom).
  **jsdom 이 판정할 수 없는 부류가 있다**(레이아웃·캔버스 픽셀) — 그건 사람 체크리스트로 넘긴다.
- **스키마를 바꿨다면 마이그레이션 자체를 테스트한다.** 모델이 맞는 것과 마이그레이션이
  도는 것은 다른 문제다. up → down → up 왕복, 그리고 **기존 데이터가 있는 상태에서의 up**
  (운영에는 175행이 있다, 2026-09-27)을 확인한다. 기존 `test_migration_*.py` 가 틀이다.
- **`GET /scores` 의 정렬·응답 필드를 고정하는 테스트가 이미 있는지 확인하고,
  없으면 만든다.** 웹 홈과 Flutter 앱의 공유 계약인데 지키는 테스트가 없으면
  다음 사람이 조용히 깬다.

## 셸이 이 단계 뒤에 하는 일 — red 게이트
네가 끝나면 셸이 **구현 전 코드**에서 검증 명령을 돌린다.
- **전부 통과하면 파이프라인이 죽는다.** 구현 전에도 통과하는 테스트는 바뀔 동작을 검사하지
  않는 것이다 (항상 참인 단언, 구현과 무관한 기대값, 러너가 새 파일을 안 도는 위치).
- 실패해야 다음 단계(구현)로 넘어간다. 구현 뒤 같은 명령이 통과하면(green) 완주다.
- 구현은 네 테스트를 **한 글자도 못 고친다.** 테스트가 틀리면 구현이 BLOCKED 로 멈춘다 —
  그러니 설계의 기대값을 정확히 옮겨라.

## 할 일
1. DESIGN.md 의 검증 기준을 실행 가능한 테스트로 옮긴다. 기준 하나당 케이스가 최소
   하나씩 대응돼야 한다. **이전 주행이 죽으면서 일부 테스트 파일을 남겼을 수 있다** —
   처음부터 다시 쓰지 말고, 이미 덮인 기준을 확인한 뒤 모자란 것만 보태라.
2. **설계가 바꾸는 동작을 전제로 쓰인 기존 테스트를 새 동작에 맞게 고친다.** 구현은 테스트를
   못 고치므로 지금 너만 할 수 있다. 지우지 말고 고쳐라 — 지우면 그 기준의 회귀 방어가
   사라진다. 정말 무의미해진 케이스만 지우고 이유를 VERIFY.md 에 써라.
3. **의심한 곳만 검증하면 의심한 것만 잡힌다.** 검증 기준에 없더라도 설계가 건드리는
   경계(NULL, 빈 목록, 중복, 순서, 동시성)를 찾아 케이스를 추가한다.
4. 허용된 테스트 명령을 **실제로 돌려** 새 테스트가 **올바른 이유로** 실패하는지 확인한다.
   - 올바른 실패: 기대값 불일치, 아직 없는 함수·엔드포인트 (구현하면 풀린다)
   - 잘못된 실패: 테스트 파일의 문법 오류, 잘못된 import 경로, 픽스처 누락 (구현해도 안 풀린다)
   잘못된 실패는 고친다. 명령이 거부되면 우회하지 않고 그 사실을 적는다.
5. **테스트로 못 덮는 것을 사람 체크리스트로 넘긴다.** "무엇을 하면 무엇이 보여야
   하는가" 수준의 재현 절차로 쓴다.

## 테스트를 쓸 때 지킬 것
- **구조 불변식은 값이 통째로 바뀌어도 통과한다.** "필드가 3개다", "리스트가 비어있지 않다"
  같은 단언은 회귀를 못 잡는다. **값을 고정**하거나 관계를 단언한다.
- skip / xfail / 항상 참인 단언으로 케이스 개수만 채우지 않는다.
- 외부 호출은 mock 으로 막는다. 실제 네트워크·타이밍에 기대는 테스트는 다른 PC 에서
  무작위로 깨진다 — 이벤트 수신 자체가 아니라 **받은 뒤의 판정 로직**을 순수 함수로 테스트한다.
- 아직 없는 인터페이스는 **설계에 적힌 이름·시그니처 그대로** 부른다. 네가 지어내면 구현이
  다른 이름으로 만들고, 구현은 테스트를 못 고치므로 거기서 막힌다.

## VERIFY.md 필수 섹션
- STATUS 라인 (첫 줄)
- 작성·수정한 테스트 파일과 케이스 목록
- 검증 기준 ↔ 테스트 케이스 대응표 (**빠진 기준이 있으면 명시**)
- **각 테스트가 무엇을 깨면 실패하는지** 한 줄씩 — 이게 없으면 통과해도 의미를 모른다
- **지금(구현 전) 돌렸을 때의 실패 내용** — 명령과 실제 출력 요약. 못 돌렸으면 그 이유
- 구현이 알아야 할 것 — 테스트가 부르는 인터페이스(이름·시그니처·반환값)
- 테스트로 덮지 못한 부분 + 사람이 확인할 것 체크리스트 (재현 절차)

## 중요
- 통과·실패 판정은 **이 세션이 하지 않는다.** 셸이 red·green 을 직접 돌려 판정한다.
- **설계가 틀렸거나 검증 기준이 테스트로 옮길 수 없을 만큼 모호하면 `STATUS: BLOCKED`.**
  추측으로 기대값을 채우지 마라 — 구현이 그 추측에 묶인다.

## 금지
- **제품 코드를 고치지 않는다.** 구현을 미리 써 두면 red 가 사라지고, 소스 파일은 셸이 지문으로 막는다.
- 패키지를 추가하지 않는다. 필요하면 BLOCKED.
- **테스트 러너·린터·타입 검사 설정을 수정하거나 새로 만들지 않는다.** 게이트를 느슨하게
  만드는 가장 값싼 경로라 셸이 지문으로 감시한다. 픽스처가 필요하면 테스트 파일 안에 둬라.
- DESIGN.md·JUDGE.md 를 수정하지 않는다. 셸이 지문으로 감시한다.
